# VANTAGE — Data Architecture & Schemas

## 1. Domain Entities & Relational Schemas

Vantage structures all collected information around normalized, relational schemas with full lineage tracking.

```
┌─────────────────┐       ┌─────────────────┐       ┌─────────────────┐
│     Source      │──────<│   Observation   │>──────│     Entity      │
│ (Platform/Auth) │       │  (Time-Series)  │       │ (Repo/Author/Pkg│
└─────────────────┘       └────────┬────────┘       └────────┬────────┘
                                   │                         │
                                   ▼                         ▼
                          ┌─────────────────┐       ┌─────────────────┐
                          │     Signal      │       │  Relationship   │
                          │ (Anomaly/Burst) │       │ (Co-occurs/Uses)│
                          └────────┬────────┘       └─────────────────┘
                                   │
                                   ▼
                          ┌─────────────────┐
                          │  Investigation  │
                          │  (Agent Dossier)│
                          └─────────────────┘
```

## 2. Core Table Definitions

### 2.1 `entities`
Represents any identified subject (a GitHub repository, a PyPI package, an AI model, a developer, or a topic):
- `id` (TEXT, Primary Key, UUID)
- `name` (TEXT, e.g., "fastapi/fastapi", "qwen-2.5")
- `entity_type` (TEXT, enum: `repository`, `package`, `model`, `paper`, `author`, `topic`)
- `primary_url` (TEXT)
- `description` (TEXT)
- `metadata` (JSON)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

### 2.2 `observations`
Raw time-stamped metric recordings:
- `id` (TEXT, Primary Key, UUID)
- `entity_id` (TEXT, Foreign Key -> `entities.id`)
- `source_id` (TEXT, e.g., "github_api", "huggingface_hub")
- `metric_name` (TEXT, e.g., "stars", "downloads", "forks", "citations")
- `metric_value` (FLOAT)
- `observed_at` (TIMESTAMP, ground truth observation time)
- `collected_at` (TIMESTAMP, system ingestion time)

### 2.3 `signals`
Statistically significant shifts detected in time-series metrics:
- `id` (TEXT, Primary Key, UUID)
- `entity_id` (TEXT, Foreign Key -> `entities.id`)
- `signal_type` (TEXT, enum: `growth_surge`, `velocity_spike`, `anomaly`, `cross_platform_emergence`)
- `z_score` (FLOAT, statistical deviation)
- `velocity` (FLOAT, current rate of change $\frac{\Delta M}{\Delta t}$)
- `acceleration` (FLOAT, second derivative $\frac{\Delta^2 M}{\Delta t^2}$)
- `confidence` (FLOAT, 0.0 to 1.0)
- `status` (TEXT, `active`, `resolved`, `investigating`)
- `detected_at` (TIMESTAMP)

### 2.4 `investigations`
Dossiers generated by multi-agent research:
- `id` (TEXT, Primary Key, UUID)
- `entity_id` (TEXT, Foreign Key -> `entities.id`)
- `signal_id` (TEXT, Nullable, Foreign Key -> `signals.id`)
- `title` (TEXT)
- `summary` (TEXT)
- `evidence_sources` (JSON, list of cited URLs, titles, dates)
- `key_findings` (JSON, list of verified conclusions)
- `confidence_score` (FLOAT)
- `created_at` (TIMESTAMP)

## 3. Data Lineage & Timestamp Governance

Every data record strictly records four distinct temporal dimensions:
1. **`event_time`**: When the event originally happened in the real world (e.g. paper publication date, commit timestamp).
2. **`observed_at`**: When the metric value snapshot was recorded on the external platform.
3. **`collected_at`**: When Vantage ingested and validated the record.
4. **`inferred_at`**: When the analytics engine computed the derived signal or prediction.
